## 1. 一句话,这个项目在做什么

**给快餐店店长做一个"次日鲜食订货量"的预测工具,但它的特别之处不是预测准不准,
而是它知道自己什么时候不该给答案。**

店长每天要给大概40个短保质期商品(比如生菜、番茄片)下次日订单。传统做法是"上周卖多少,
今天就订多少,再加点余量防止不够卖"——多订的部分卖不掉就得扔。FreshCall 想做的不是
"训练一个更准的预测模型"(这条路早就有人做了,比如 Crunchtime、ClearCOGS),而是解决
一个这些工具都没解决的问题:**它们给出一个数字,但从不告诉店长这个数字该不该信**。

FreshCall 的做法:对每个商品,模型不仅给一个建议订货量,还会判断"我对这个预测有没有把握"。
没把握的时候,它不硬给一个数字冒充自信,而是直接说"ASK ME——这个我说不准,你来判断",
把决策权交还给人。

**你需要能一句话讲出这个"差异化"**:别人是"预测得准不准",我们是"知道自己什么时候
不该预测"。

## 2. 谁在用,为什么要用

- **用户**:快餐店店长,晚班快结束时,在手机上花几十秒下第二天的鲜食订单。
- **场景约束**(这些约束决定了很多设计选择,不是随便定的):
  - 店长很忙,只有一个屏幕、几十秒时间——所以订货量必须直接以"箱数"呈现,不是"件数"。
  - 店长没有"预测区间"这种概念——所以界面上**永远不能出现一个"置信度XX%"的数字**,
    这也是为什么我们把 `confidence` 定为整个代码库的禁用词(见 `CONTEXT.md`)。
  - 店长对某些商品有自己的经验判断——所以任何建议都必须"可以被推翻",推翻不算系统失败。

## 3. 系统架构:为什么是这三层,不是别的组合

FreshCall 是一个"混合架构",三个部分각自负责不同的事,**故意不让同一个组件干两件事**:

| 负责什么 | 用什么做 | 为什么不用别的 |
|---|---|---|
| **预测次日需求** | scikit-learn 的分位数回归(quantile GBR),同时给出低估计(P10)/中估计(P50)/高估计(P90) | 用 LLM 做这件事,给不出一个有统计意义的"区间";而且同样的输入,LLM 每次可能给出不同答案(非确定性),这对"要不要弃权"这种需要复现的判断是致命的。 |
| **算订货箱数 + 判断要不要弃权** | 纯 Python,确定性代码,零 AI 参与 | 这里算错是真金白银的错误(多订一箱就是实打实的浪费)。确定性代码可以写单元测试、可以复现、可以审计;AI 在这里参与,等于让一个不可控的东西碰钱。 |
| **把结果写成一句人话** | 租用的 gpt-4o-mini | 这一步只是"把已经算好的事实,用自然语言说出来"——错一个词最多让店长多看一眼,不会让订货量算错。这是唯一允许 LLM 参与、且允许它"犯错代价很低"的地方。 |

**你需要能回答的追问**:"如果全部用一个大模型来做,不行吗?" —— 答案:分位数区间需要
统计上的校准(能不能保证80%的时候真实值落在区间内),这是训练出来的模型才能给的保证,
LLM 自己说"我有80%把握"是编的,没有校准依据。

## 4. "弃权"这件事具体怎么算出来的

这是整个项目的核心机制,必须能脱稿讲清楚:

1. 模型给出三个数:P10(悲观估计)、P50(中间估计)、P90(乐观估计)。
2. 算一个"区间相对宽度":`rel_width = (P90 - P10) / P50`。
   直觉:如果模型很有把握,P10和P90会很接近,这个数字就很小;如果模型很没把握
   (比如遇到了训练时没见过的情况),这个区间会被自动撑得很宽。
3. 如果 `rel_width` 超过一个阈值(暂定0.60,后续会用真实回测数据在
   0.40/0.50/0.60/0.70 四档里选一个最终值),系统就**拒绝给出订货建议**,
   转而显示 "ASK ME"。
4. 弃权时,系统会附带一个**参考锚点**——"上周同一天你实际订了几箱"——这是一个
   历史事实,不是模型算出来的东西,所以不违反"不能显示置信度数字"这条设计原则,
   但能让店长不至于两眼一抹黑。

**关键区分**(容易被问倒的地方):`rel_width` 只能捕捉"这个商品本身波动大不大"
(统计学叫 aleatoric uncertainty,天生的随机性),**捕捉不了**"这是不是一个模型
从没见过的全新情况"(epistemic uncertainty,比如突然地震、突然搞活动)。后者需要
另一套机制(新颖性检测,比如 IsolationForest)来兜底,但这个我们决定**先不做**,
等主链路跑通、第一个 gate 验证过再加——两个互相影响的 gate 一起从零开始调,出问题
分不清是哪个的锅。

## 5. 数据:这份数据到底扮演什么角色(上一轮已经详细聊过,这里只放结论)

用的是 Kaggle 上厄瓜多尔连锁超市 Corporación Favorita 公开的真实销售数据
(54店、4年半、1.25亿行)。**这不是完美契合的数据**(超市≠快餐店,而且没有库存字段),
但也**不需要去找"更契合"的数据**——那种数据(快餐店+真实库存)因为涉及商业机密,
基本不可能公开存在。

这份数据的角色是一个**方法论验证台架**:它用来回答"我这套'预测+算不确定性+决定弃权'
的机制,在真实、有噪声的销量数据上,到底跑不跑得通、校准合不合理",而不是回答
"这套系统放到真实快餐店里效果多好"。这个边界,我们用 **Layer A(需求预测+不确定性+
弃权,这份数据能验证)** 和 **Layer B(考虑库存的最优订货,这份数据验证不了)**
两个词严格分开了(定义见 `CONTEXT.md`)。

**已经跑出来的真实数字**(不是估计):
- 54店、4,100个商品、986个易腐商品——跟官方数据说明完全对得上。
- 退货(负数销量)只占0.004%,占比极低,所以"保留原始负值不做处理"这个决定成本很低。
- 986个易腐商品里,72%(707个)是整数销量(能按箱订货),28%是按重量卖的(排除,
  因为没有"箱"这个概念)。
- **44号店**在所有密度阈值下,可选的高质量商品数量都是全店最多的(密度阈值0.7时有537个)。
- 第一个用来跑通最小可行版本的商品:**502331号(面包类)**,1679天里1671天都有记录,
  几乎没有缺口——选它是为了确保"代码有没有bug"和"数据本身缺口太多"这两类问题不会
  混在一起,干扰你判断问题出在哪。

## 6. 怎么知道这个系统做得好不好(评估计划)

**核心指标改名了**(原来叫 CPOA/"Case-Pack Order Accuracy",现在改叫
**Case Match Rate(CMR)**):建议订货箱数,跟"事后已知真实销量折算出的箱数"
(`hindsight_demand_order`)对上的比例。改名是因为原名字暗示我们在验证"订货
最优性",但没有库存数据,我们验证不了这个,只能验证"需求折算准不准"。

四项检查,**按"如果这项失败,会让哪些结论作废"的顺序排**:

1. **区间校准检查**(最先做):P10-P90 区间,实际有没有真的80%的时候包住真实值?
   如果远低于80%,后面所有"弃权精度"之类的数字都没有意义——因为区间本身就是
   编出来的,不是真实的不确定性度量。
2. **时间切分回测,三折滚动(rolling-origin),不是单次**:原计划只测
   2017-07-16到08-15这31天,老师反馈指出——单独一段回测,万一刚好撞上一个假期
   周末,整个"好"或"坏"的结论就被这一个巧合事件绑架了,证明不了方法本身行不行。
   改成三折,比如 5/16–6/15、6/16–7/15、7/16–8/15 各自训练+测试一次,**三折结果
   分开报,不揉成一个平均数**——如果三折表现接近,说明结果稳定;如果某一折特别差,
   那本身就是个值得深挖的发现,不是失败。这个改动幾乎零成本,只是把同一套代码
   多跑两次。仍然**不声称"统计显著性"**——每折31天依然是相关的日子,不是独立样本,
   只是三折比一折更难被单一巧合绑架。
3. **弃权阈值扫描**:0.40/0.50/0.60/0.70 四档,画出"弃权率 vs 弃权精度"的曲线,
   最终操作点从曲线上选,不是拍脑袋先定死。
4. **解释校验(L1/L2)**:L1是硬性检查——LLM 输出里的每一个数字,都必须能在给它的
   "事实块"里找到,一个字都不能编;L2是找一个更强的模型当裁判,评价语气/是否贴切。
   10个测试案例,按 `rel_width` 分层抽样(高/中/低不确定性都要覆盖到),规则提前
   写进代码里,不是等结果出来了再挑好看的案例。

**一个容易踩的坑,老师也点出来了——Naive_seasonal 必须跟模型比在同一批案例上**:
CMR 只在"模型选择回答"的那部分 SKU-day 上计算(弃权的案例被甩给了人)。如果
baseline(Naive_seasonal)是在**全部**案例上算准确率,而模型是在它自己挑出来的
**"简单"**案例上算准确率,这个对比是不公平的——模型看起来"更准",可能只是因为
它把难的都推给了人,不是真的更聪明。**正确做法**:Naive_seasonal 也只能在
"模型选择回答"的那同一批 SKU-day 上计算,两边比的才是"面对同一批案例,谁做得好",
不然15%的提升可能只是选择偏差(selection bias),不是真本事。

**放弃条件**(项目最诚实的一部分,请记住):如果在15%弃权率下,弃权精度并不比
随机选商品好,就应该老实承认——这个问题需要更快的事后异常检测,而不是弃权机制,
并且把这个结论如实写进报告,而不是硬凹一个好看的数字。

## 8. 接下来怎么实现(分阶段,每阶段有明确的"过关标准")

### 阶段 1 —— 最小可行版本(§8,单 SKU、90 行数据)
**目标**:证明"预测 → 判断弃权 → 算箱数 → 写一句话"这条链路本身没有硬伤。

- 用商品502331(44号店)导出90行日销量数据(约12周的历史)。
- 特征:星期几、前一天销量(lag-1)、前七天销量(lag-7)、过去7天平均(rolling-7 mean),
  全部用 `.shift(1)` 保证不会用到"未来"的数据(防止数据泄漏)。
- 用前83行训练三个分位数回归模型(P10/P50/P90),预测第84天。
- 算 `rel_width`,跟阈值0.60比较,决定是"给数字"还是"ASK ME"。
- 用确定性 Python 算箱数(`case_pack=12`, `safety=0`, `on_hand=0`)。
- 调一次 gpt-4o-mini,把算好的事实包成一句话。

**过关标准(全部自动化,不是我说了算,是代码断言说了算)**:
1. 全流程在干净环境里60秒内跑完。
2. 订货件数一定是12的整数倍(代码里 assert,不是靠肉眼看)。
3. LLM 输出的每个数字,必须能在"事实块"里找到——一个不在里面就算失败,零容忍。
4. 故意造一个高波动的输入,系统必须输出不带任何数字的弃权文案。

### 阶段 2 —— 扩大到多个 SKU + 完整回测
把阶段1的逻辑套到44号店的537个候选商品上(或者其中一个合理子集),跑§6提到的
四项评估检查,得到真实的 CMR、弃权率、弃权精度、区间校准数字。

### 阶段 3 —— 完善弃权机制(可选,视时间而定)
如果阶段2的校准检查通过、时间还够,再加日历规则(节假日/地震这类已知事件强制弃权)
和新颖性检测(IsolationForest)。

### 阶段 4 —— 界面(往后放,不是现在的重点)
核心逻辑跑通、评估数字都拿到手之后,如果还有时间,套一个简单的 Streamlit 页面。
视频演示不一定需要网页界面——终端输出配合讲解,同样能讲清楚架构。

### 阶段 5 —— 写作与演示(等老师给要求再动)
≤1200字的 trade-off analysis(可以直接从 `DECISIONS.md` 提炼)、录屏演示。
